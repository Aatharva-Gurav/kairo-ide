# 08 — Transport Contract Specification

## 1. Overview & Transport Protocol

Communication between the Kairo IDE frontend (Next.js) and the internal AI coding-agent backend (Bun sidecar) occurs over a dedicated, low-latency, loopback-only **WebSocket connection**.

This design mirrors and standardizes the architecture found in the official Cline desktop application while introducing strict end-to-end type validation using **Zod** and TypeScript interfaces.

- **Endpoint URL**: `ws://127.0.0.1:<port>/transport?approval_token=<token>`
- **Serialization Format**: UTF-8 encoded JSON.
- **Protocol Version**: `1.0.0`
- **Max Payload Size**: 16 MB (sufficient for large unified diffs and multimodal image payloads).
- **Default RPC Timeout**: 30,000 ms (30 seconds) with cancelable tasks.

## 2. Wire Frame Envelopes

Every WebSocket frame exchanged adheres to one of three discriminated envelope schemas:

```
                  ┌──────────────────────┐
                  │   WebSocket Stream   │
                  └──────────┬───────────┘
                             │
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
│ Command Envelope│ │Response Envelope│ │ Event Envelope  │
│(Client -> Server│ │Server -> Client)│ │(Server -> Client│
│  type: "command"│ │ type: "response"│ │  type: "event"  │
└─────────────────┘ └─────────────────┘ └─────────────────┘
```

### 2.1. Command Envelope (Client -> Server)
Sent by the frontend to invoke an RPC action on the backend.

```typescript
export interface CommandEnvelope<TName extends string = string, TParams = unknown> {
  type: "command";
  id: string;               // Unique UUID v4 generated by client
  name: TName;              // Command name identifier
  params: TParams;          // Strongly-typed payload parameters
}
```

### 2.2. Response Envelope (Server -> Client)
Sent by the backend in direct response to a Command Envelope matching the same `id`.

```typescript
export interface SuccessResponseEnvelope<TResult = unknown> {
  type: "response";
  id: string;               // Matches the request command id
  status: "ok";
  result: TResult;
}

export interface ErrorResponseEnvelope {
  type: "response";
  id: string;               // Matches the request command id
  status: "error";
  error: {
    code: string;           // E.g. "ERR_NOT_FOUND", "ERR_INVALID_PARAMS", "ERR_TIMEOUT"
    message: string;        // Human-readable diagnostic message
    details?: unknown;      // Optional structured error information
  };
}

export type ResponseEnvelope<TResult = unknown> = 
  | SuccessResponseEnvelope<TResult> 
  | ErrorResponseEnvelope;
```

### 2.3. Event Envelope (Server -> Client)
Unsolicited or streaming notifications pushed from the backend to the frontend.

```typescript
export interface EventEnvelope<TEvent extends string = string, TPayload = unknown> {
  type: "event";
  event: TEvent;            // Event name identifier
  sessionId?: string;       // Associated agent session ID if applicable
  taskId?: string;          // Associated task/turn ID if applicable
  seq: number;              // Monotonically increasing sequence number per session
  timestamp: number;        // Epoch timestamp in milliseconds
  payload: TPayload;        // Strongly-typed event payload
}
```

Upon establishing the WebSocket connection, the frontend immediately transmits a `handshake` command to verify protocol compatibility.

```typescript

  clientVersion: z.string(),
  protocolVersion: z.string(),
```

## 4. Server Push Event Specifications

The backend delivers real-time token streams, status updates, and tool approval triggers via the following events:

| Event Name | Payload Description | Trigger Condition |
| :--- | :--- | :--- |
| `session_state_changed` | Full session status snapshot (`mode`, `busy`, `activeTaskId`) | State transitions between idle/busy/error |
| `message_created` | User or assistant message header record | Start of message generation |
| `token_delta` | Streaming text snippet: `{ delta: string }` | Model outputs next tokens |
| `reasoning_delta` | Streaming reasoning snippet: `{ reasoningDelta: string }` | Model outputs thinking tokens |
| `tool_approval_request` | Pending tool details: `{ approvalId, toolName, arguments, diffPreview? }` | Model requests mutating action requiring user consent |
| `tool_execution_start` | Tool notification: `{ toolName, callId }` | Tool execution commences after approval |
| `tool_execution_result` | Tool output: `{ callId, success: boolean, output: string }` | Tool process completes |
| `task_completed` | Turn summary: `{ taskId, totalTokens, finishReason }` | Agent turn terminates cleanly |
| `task_error` | Error details: `{ taskId, errorCode, message }` | Fatal provider or runtime error |
| `token_usage_updated` | Context usage: `{ inputTokens, outputTokens, totalCost }` | Turn completes or streaming milestone |

## 5. Reconnection & Resilience Protocol

### 5.1. Heartbeats & Keep-Alive
- **Ping Interval**: The frontend sends a lightweight ping frame every 15,000 ms.
- **Pong Expectation**: The backend responds with a pong.
- **Timeout Threshold**: If no pong or message is received for 35,000 ms, the frontend considers the connection dead, closes the socket, and initiates reconnection.

### 5.2. Reconnection Strategy
- **Exponential Backoff**: Reconnect attempts use jittered exponential backoff:
  $T = \min(1000 \times 1.5^{\text{attempt}}, 10000) \pm \text{jitter}$
- **Max Retries**: Unlimited while the Tauri window is open; UI indicates "Backend reconnecting...".

### 5.3. Sequence Numbering & Drop Detection
- Every event emitted by the server increments `seq` by 1 within that `sessionId`.
- If the frontend detects a gap in sequence numbers ($seq_{received} > seq_{last} + 1$), it automatically requests a state sync via `load_session` to rehydrate any missed events without corrupting local state.

## 6. Security & Framing Limits

1. **Authentication Token Verification**:
   Incoming upgrade requests must provide `?approval_token=<token>` matching the secret token passed to the sidecar at startup by Tauri. Missing or invalid tokens result in an immediate `401 Unauthorized` HTTP response.
2. **Payload Size Guard**:
   Max frame size is capped at 16,777,216 bytes (16 MB). Any frame exceeding this limit triggers connection termination to prevent heap exhaustion attacks.
3. **Loopback Only**:
   The WebSocket server explicitly binds to `127.0.0.1` and verifies the `Host` and `Origin` headers against allowed origins (`tauri://localhost`, `http://localhost:3000`).
